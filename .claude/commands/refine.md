아래 요청을 바로 구현하지 말고, 다음 단계에 따라 작업 프롬프트로 정리한다.

요청: $ARGUMENTS

## 1단계: 해석
- 무엇을, 어디에, 어떤 조건으로 하려는지 정리한다.
- 관련 파일과 기존 구현을 찾아 읽는다.
- PRD의 MVP 제외 목록이나 `docs/decisions.md`와 충돌하면 여기서 멈추고 보고한다.
- 결과에 큰 영향을 주는 모호점이 있으면 질문을 최대 3개까지 한다. 사소한 건 가정하고 표시한다.

## 2단계: 기존 해법 확인
다음 경우에만 수행하고, 아니면 "해당 없음"이라고 적고 넘어간다.
- 대상: 흔한 UI 부품(토스트, 모달, 드롭다운, 날짜 선택, 드래그 앤 드롭, 차트, 무한 스크롤, 리치 텍스트, 파일 업로드 등)이나 표준 문제(폼 검증, 날짜·시간대, 인증, 결제, 검색, 이미지 처리, 캐싱, 재시도 등)
- 건너뜀: 도메인 로직, 기존 코드 수정·버그 수정, 사용자가 라이브러리를 이미 지정한 경우

순서:
0. `docs/decisions.md`의 기본 부품 표에 같은 용도가 있으면 그것을 따르고 확인을 끝낸다.
1. 프레임워크 내장 기능이나 이미 설치된 의존성(`package.json`, `pubspec.yaml`, `requirements.txt` 등)으로 해결되는지 확인한다.
2. 아니면 후보 라이브러리 2~3개를 조사한다. 버전과 상태는 기억이 아니라 공식 문서나 레지스트리(npm, pub.dev, PyPI)에서 확인한다.
   확인 항목: 최근 릴리스, 현재 스택 버전과의 호환, 라이선스, 크기·의존성, 설정 난이도
   웹 조회가 불가능하면 "미확인"으로 표시하고, 사용자가 직접 확인할 항목을 적는다.
3. 직접 구현할 경우의 대략적인 구현량과 빠지는 기능(접근성, 애니메이션, 엣지 케이스)을 적는다.
4. 보안 영역(인증, 암호화, 결제)을 직접 구현하려는 요청이면 위험을 한 줄로 경고한다.

출력:

### 기존 해법 확인: {기능}
| 선택지 | 종류 | 장점 | 단점 |
| --- | --- | --- | --- |
| | 내장 / 기존 의존성 | | |
| | 라이브러리 | | |
| 직접 구현 | - | | |

**추천:** {하나} — {이유 한두 줄}
**확인 출처:** {링크 또는 "미확인"}

선택지를 안내했으면 여기서 멈추고 사용자의 선택을 기다린다.

## 3단계: 작업 프롬프트
사용자가 고르면(또는 2단계가 해당 없음이면) 아래 형식으로 정리한다.

```markdown
## 목표
(한 문장)

## 범위
- 수정 대상:
- 하지 말 것:
- 새 패키지: 금지 / 허용: {이름} (버전은 설치 시 최신 안정 버전 확인)

## 완료 기준
- (관찰 가능한 결과. "비슷하게" 대신 "무엇은 유지하고 무엇을 바꾼다")

## 검증
- 테스트 수준: {decisions.md 기준 또는 이번 작업 예외}
- 실행할 명령 / 확인할 화면:

## 참고
- 관련 파일:
- 사용한 가정:

## decisions.md에 남길 줄
- (기본 부품 선택 등, 없으면 "없음")
```

작업 프롬프트를 보여준 뒤 "이대로 진행할까요?"라고 묻고, 승인을 받으면 CLAUDE.md 규칙에 따라 구현한다. 승인 전에는 파일을 수정하지 않는다.

## 4단계: 기록
2단계에서 사용자가 선택지를 골랐다면, 진행 승인과 함께 다음을 직접 수행한다. 사용자가 따로 명령을 입력하기를 기다리지 않는다.
- `docs/decisions.md` 기본 부품 표에 선택을 반영하고, 변경 로그에 `- YYYY-MM-DD | 결정 | 이유 | 영향 문서` 한 줄을 추가한다.
- 다른 문서에 영향이 있으면 `.claude/commands/decide.md`의 3~5단계를 따른다.
- 결과 보고에 기록한 줄을 포함한다.
