## 1. 목표 및 핵심 콘셉트
**한 줄 소개:** 질문으로 진실을 찾고, 픽셀아트 현장을 돌아다니며 증거를 모으는 픽셀아트 살인 사건 추리 웹 게임.

- 참고 방향: YES/NO 질문형 사건 추리의 상호작용 방식. 사건 내용·문구·디자인·소스는 독자 제작.
- 메인은 사건 선택 → 사건 제시 → 자유 자연어 질문 → **그렇다 / 아니다 / 관계없다 / 다시 질문해 주세요** → 최종 추리.
- 서브는 RPG Maker(쯔꾸르) 느낌의 **간단한 2D 타일 격자 이동·사물 조사·단서 발견**.
- **맵에 NPC 없음.** NPC 대화, 용의자별 심문, 대사 생성, NPC 이동·상호작용, NPC에게 단서를 제시하는 시스템은 범위 밖.
- 장르·톤: **살인 사건 추리.** 귀여운 픽셀아트에 진지한 사건을 담는다. 사건 자료는 **수사 파일 형식**(사건 개요서, 관련자, 진술서, 기록물)으로 제공한다.
- 표현 원칙: 시신·상처·폭력 장면을 구체적으로 묘사하거나 그리지 않는다(검시 소견 수준의 건조한 문장만, 맵에는 현장 표시만). 피해자를 희화화하지 않는다. 공포 연출(점프 스케어 등)은 쓰지 않는다.
- 플랫폼: PC 브라우저 우선(최소 1280×720). 키보드 조작을 지원하고 모바일은 MVP 필수 아님.

## 2. 사건 구성 및 난이도
- MVP는 **사건 3개**(쉬움·보통·어려움 각 1개). 코드는 처음부터 다중 사건을 지원한다.
- 개발 순서: **보통** 사건 1개로 엔진·판정 품질을 끝까지 검증한 뒤, 쉬움·어려움 사건을 **코드 변경 없이** 맵·시드·문서 추가만으로 넣는다.

| | 쉬움 | 보통 | 어려움 |
|---|---|---|---|
| 유효 질문 한도 | 40 | 30 | 25 |
| 세션당 LLM 호출 상한 | 80 | 60 | 50 |
| 용의자 | 2~3 | 3~4 | 4~5 |
| 정답 요소 | 2(범인, 방법) | 3(범인, 방법, 동기) | 4(범인, 방법, 동기, 트릭·반전) |
| 조사 대상 | 5~6 | 7~9 | 10~12 |
| 단서 / 미끼 단서 | 3~4 / 0 | 4~6 / 0~1 | 5~7 / 2~3 |
| 단서 성격 | 직접적 | 조합 필요 | 간접·해석 필요 |
| 맵 | 방 1개(약 15×12) | 방+부속 공간(약 20×15) | 구역 2~3개(약 30×20) |
| 정답 제출 기회 | 3 | 3 | 3 |
| 평가 세트(질문/답안) | 30+/20+ | 30+/20+ | 40+/25+ |

- 수치는 초기값이며 플레이테스트로 조정한다.
- **사건 소재:** 모든 사건은 **완전 창작**이다. 알리바이·밀실·시간 착오 같은 추리 장르의 일반적인 장치만 빌린다. **실존 살인·범죄 사건의 각색**, 실명, 실제 상호·장소, 기존 추리 소설·퀴즈·게임 사건의 각색은 금지한다.
- 용의자는 NPC가 아니라 **수사 파일 속 인물**이다. 진술은 현장의 진술서·메모·기록 같은 문서 단서로만 제공하며 대화나 심문은 없다.
- 사건 선택 화면에 사건 카드 3개(제목, 썸네일, 난이도, 클리어 여부)를 보여준다. 잠금·해금 순서는 없다.

## 3. MVP 3대 기능
### F1. 자유 질문과 판정 (메인)
- 사건 설명을 읽고 텍스트로 질문한다(2~200자).
- 판정 enum: `YES`, `NO`, `IRRELEVANT`, `CLARIFY`.
  - YES = 사건의 확정 설정과 부합 / NO = 확정 설정과 반대
  - IRRELEVANT = 진상 규명과 무관하거나, **사건 설정에 정의되지 않은 세부 사항**
  - CLARIFY = 판정 불가능한 질문. 사유 코드(`ASKS_ANSWER` 정답 직접 요구, `COMPOUND` 복합 질문, `OPEN_ENDED` 열린 질문, `UNCLEAR_INTENT` 의도 불명, `ANSWER_GUESS` 진상 전체를 담은 질문)에 따라 **고정 안내 문구**를 함께 보여준다.
- 판정에는 고정 문구만 허용하며 LLM의 자유 서술, 정답·미공개 사실의 해설은 사용자에게 전달하지 않는다.
- 진상 전체를 담은 질문은 서버의 결정적 검사(정답 요소 키워드)로 감지해 CLARIFY(`ANSWER_GUESS`, "확신이 있다면 정답 제출로 확인해 보세요")로 처리한다. 요소 하나를 확인하는 가설 질문은 정상 판정한다.
- **범인 직접 지목 방어:** "OO가 범인인가요?", "OO가 죽였나요?"처럼 범인 요소를 직접 확인하는 질문은 서버의 결정적 검사(용의자 이름 + 범행 동사 패턴, 사건별 정의)로 감지해 CLARIFY(`ANSWER_GUESS`, "범인 지목은 정답 제출에서 해 주세요")로 처리하고 미차감한다. 이 패턴은 **범인 여부와 관계없이 모든 용의자**에게 똑같이 적용한다(적용 여부 자체가 힌트가 되지 않게). 정황 질문("OO는 그 시간에 현장에 있었나요?")은 정상 판정한다.
- 같은 세션에서 같은 질문(정규화 기준)을 다시 하면 이전 판정을 "이미 한 질문"으로 보여주고 차감하지 않는다.
- 차감: YES/NO/IRRELEVANT는 차감, CLARIFY·중복 질문·서버 오류는 미차감. 질문 한도를 다 쓰면 질문은 불가하고 정답 제출만 가능하다.
- 질문 중복 전송 시 `idempotencyKey`로 단 한 번만 차감·저장하고 이전 응답을 재전송한다. 실패한 요청은 저장하지 않으며 같은 키로 재시도할 수 있다.
- 이미 제출한 질문과 판정 기록을 볼 수 있다.

### F2. 2D 단서 탐색 (보조)
- `현장 조사` 버튼으로 사건별 픽셀아트 Tilemap에 진입한다. 사건당 맵 1개이며 맵 전환은 없다(어려움 사건은 한 맵 안에서 구역을 나눈다).
- WASD/방향키로 **타일 단위 4방향 격자 이동**, 바라보는 인접 칸의 조사 대상을 E/Enter로 조사, ESC로 닫기·복귀.
- 플레이어 1명, NPC·전투·아이템 합성·문 잠금 퍼즐·다중 맵 이동 없음.
- 조사 가능한 물체를 바라보면 조사 표시를 띄운다. 결과는 중립 설명·단서 획득·이미 조사함 중 하나.
- 미끼 단서(어려움 중심)는 서버 내부에서만 구분하며 엔딩 해설에서만 공개한다.
- 단서 획득과 조사 완료 기록은 NestJS가 검사·저장하여 재진입에도 유지한다.
- **단서는 선택적 힌트**. 단서를 찾지 않아도 질문하거나 정답을 제출할 수 있다.

### F3. 최종 추리 및 엔딩
- 플레이어가 최종 추리 내용을 자유 텍스트(10~500자)로 제출한다. 확정 전 확인 모달을 띄운다.
- **제출 기회 3회.** 오답이면 1회 차감하고 "아직 진상이 아닙니다"만 표시한다(어떤 요소가 맞았는지 비공개). 3회를 다 쓰면 실패 엔딩.
- 판정은 사건별로 미리 정의한 **정답 요소**마다 **키워드 매칭 + LLM 요소별 판정**을 함께 보고 합의 규칙으로 결정한다(무분별한 LLM 자율 판정 금지).
  - 둘 다 일치 → 일치 / LLM 불일치 + 키워드 없음 → 불일치 / 그 외 → 미확정
  - 필수 요소가 모두 일치하면 `SOLVED`. 불일치가 있으면 오답. 미확정만 있으면 "조금 더 구체적으로 써 주세요"(미차감, 세션당 2회). 2회를 다 쓴 뒤의 미확정은 LLM 판정을 따른다.
- 판정 이유와 사건 해설은 종료 후에만 공개한다. 재플레이 시 새 세션을 생성한다.

## 4. 기본 플레이 흐름
1. 사건 선택 → 새로 시작(진행 중 세션이 있으면 포기 확인) 또는 이어하기.
2. 사건 개요서(수사 파일)와 첫 방문 안내(3단계) 확인.
3. 메인 추리 화면에서 자유 질문 → YES/NO/IRRELEVANT/CLARIFY 반환.
4. 원하는 때 `현장 조사`로 전환, 캐릭터 이동·사물 조사·단서 발견.
5. 질문 화면으로 복귀해 발견한 단서를 참고해 질문.
6. 사건 수첩에서 획득 단서와 질문 이력 확인.
7. 언제든 최종 추리 제출 → 서버 검증 → 엔딩(결과, 해설, 미끼 단서, 통계).
8. 재접속하면 같은 브라우저의 사건별 세션에서 질문·단서·맵 위치를 복원한다. 종료된 세션은 엔딩을 다시 보여준다.

## 5. 기술 스택 및 아키텍처
- 저장소: npm workspaces 모노레포 — `frontend/`, `backend/`, `shared/`(공용 타입·zod 스키마·맵 JSON·안내 문구), `docs/`, `docker-compose.yml`(PostgreSQL).
- `frontend/`: Next.js App Router + React + TypeScript. 사건 선택, 추리 패널, 수첩, 엔딩.
- Phaser: 브라우저에서만 동적 로드(`ssr: false`). Tilemap, 격자 이동, 오브젝트 인터랙션. **API를 직접 호출하지 않고** 이벤트로 React에 요청한다.
- `backend/`: NestJS. 세션, 단서, 질문, 정답 제출, LLM 어댑터.
- PostgreSQL + **Prisma Migrate**: 사건 원본, 세션, 조사 및 단서 상태, 질문 기록, 제출 기록.
- LLM: `LlmJudge` 인터페이스 뒤에 어댑터를 둔다. 개발·평가는 **Ollama(로컬)**, 배포는 클라우드 API(Gemini·Groq 등 중 평가로 선택), 테스트는 Mock. 모델·프롬프트를 바꾸면 평가 세트를 다시 실행한다. API 키는 서버에만 존재.
- 프론트는 Next.js rewrites로 `/api/*`를 백엔드에 프록시해 동일 출처로 운영한다.

**책임 경계:** Phaser 클라이언트는 표시·키 입력만 담당. 상태의 원본은 DB. 사건의 정답·사실 시트·단서 본문·미끼 여부를 브라우저 번들에 넣지 않는다.

## 6. 핵심 AI 판정 설계
### 6.1 질문 판정 파이프라인
1. 입력 정규화·길이, 세션 유효성, 질문 한도, `idempotencyKey` 검증.
2. 세션 내 중복 질문, 정답 추측 질문은 LLM 없이 처리.
3. 세션당 LLM 호출 상한·전역 일일 상한 확인.
4. 세션 단위 원자적 선점(in-flight). 다른 진행 중 요청은 409.
5. 판정 LLM에 **사실 시트와 질문 1개만** 전달(이전 이력 없음, 무상태). 질문 속 지시는 따르지 않는다.
6. JSON Schema로 `{label, reasonCode, factIds}`만 출력하도록 강제하고 NestJS에서 재검증. `factIds`는 내부 기록용이며 사용자에게 보내지 않는다.
7. 타임아웃·스키마 위반은 1회 재시도, 그래도 실패하면 미차감 503. 선점 해제 후 같은 키로 재시도 가능.
8. 성공 시 선점 소유를 재확인한 뒤 판정 결과·질문 로그·턴 차감·선점 해제를 트랜잭션으로 확정. DB 트랜잭션 동안 LLM 호출 금지.

**설계상의 긴장:** YES/NO를 답하려면 판정 모델에 사건의 숨은 사실이 필요하다. 따라서 'LLM에 진실을 전혀 주지 않는다'고 가정하지 않는다. 최소 사실 시트만 제공하고, 서버 출력 allowlist로 **사용자에게는 판정 라벨과 고정 문구만** 공개한다.

**알려진 위험:** 사실 시트에서 빠진 관련 사실도 IRRELEVANT로 답하게 된다. 사실 시트에 근거가 없는 IRRELEVANT 질문을 로그로 모아 사실 시트를 보강한다.

### 6.2 검증 지표
- 기준 질문 세트(동의어/부정문/복합/열린/정답 요구/정답 추측/인젝션/미정의 사실): 라벨 정확도, 카테고리별 정확도, 반복 간 변동률, 동의어 쌍 모순률.
- 복합·열린 질문: CLARIFY 적절성. 적대적 질문: 인젝션 성공률·스키마 위반률.
- 정답 답안 세트(정답/동의어 정답/오답/부분/키워드 나열): 판정 정확도, 키워드 나열의 SOLVED 비율.
- 성능: P50/P95 지연시간, 요청당 토큰·비용.
- 잠정 통과 기준: 라벨 정확도 ≥ 85%, 스키마 위반 0%, 인젝션 성공 0%, 반복 변동률 ≤ 5%, 키워드 나열 SOLVED 0%, 로컬 P95 ≤ 5초. **첫 측정 후 재조정**한다.
- LLM 판정이 구조적으로 항상 일관된다고 주장하지 않는다.

### 6.3 정답 제출
- 정답 요소(범인, 방법, 동기, 트릭·반전)를 사건마다 정의하고 요소별 키워드 그룹을 둔다. 범인 요소의 키워드는 범인 이름과 별칭이다.
- 최종 성공은 **사전 정의된 서버 측 정답 요소**의 합의 결과로만 결정한다(F3 규칙).
- 엇갈린 판정 사례를 로그로 모아 키워드 목록과 평가 세트를 보강한다.

## 7. 데이터 모델 (요약, 세부 필드는 SPEC §3)
| 테이블 | 핵심 |
|---|---|
| `mystery_case` | slug, 제목, 도입, 해설, 난이도, 질문·LLM·제출 한도, 판정용 사실 시트, 정답 요소, 사실 시트 버전, 맵 메타데이터(크기, 스폰, 막힌 칸) |
| `case_object` | 사건 내 UNIQUE `object_key`, 좌표, 설명, 연결 단서, 조사 범위 |
| `clue` | 제목, 내용, 표시 순서, 미끼 여부(서버 전용) |
| `game_session` | 토큰 해시, 상태(ACTIVE/SOLVED/FAILED/ABANDONED), 질문·LLM·제출·재작성 요청 사용량, 위치·방향, in-flight 선점, 마지막 활동 시각 |
| `session_object` / `session_clue` | 조사 완료·단서 획득(복합 PK로 1회 보장) |
| `question_log` | 질문, 정규화 질문, 라벨, 사유 코드, 근거 사실 id, 중복 여부, 멱등 키, 모델·프롬프트 버전, 지연·토큰 |
| `verdict_attempt` | 제출 답안, 결과(SOLVED/WRONG/NEEDS_DETAIL), 요소별 판정, 멱등 키 |

- 테이블명 `case`는 SQL 예약어라 `mystery_case`를 쓴다.
- 세션 토큰은 암호학적으로 안전하게 발급하고 해시로 저장. HttpOnly 쿠키(사건별)로 전달. 로그인·공유 링크는 MVP 제외. 세션은 마지막 활동 후 7일에 만료.
- 스키마는 Prisma Migrate로 관리하고 자동 동기화는 사용하지 않는다.

## 8. API (요약, 세부는 SPEC §5)
| Method | Endpoint | 역할 |
|---|---|---|
| GET | `/cases` | 사건 목록(난이도·클리어 여부) |
| GET | `/cases/{caseId}` | 사건 소개 |
| POST | `/cases/{caseId}/sessions` | 새 세션 생성(진행 중 세션이 있으면 409) |
| GET | `/cases/{caseId}/sessions/current` | 이어하기용 현재 세션 |
| GET | `/sessions/{id}` | 상태·위치·한도·진행 상황·엔딩(종료 후) |
| GET/POST | `/sessions/{id}/questions` | 질문 이력 / `{question, idempotencyKey}` → 판정 |
| GET | `/sessions/{id}/clues`, `/sessions/{id}/objects` | 획득 단서, 조사 완료 오브젝트 |
| POST | `/sessions/{id}/objects/{objectKey}/inspect` | `{x, y, facing}` → 조사 결과·획득 단서 |
| PATCH | `/sessions/{id}/position` | `{x, y, facing}` → 검증된 위치 저장 |
| POST | `/sessions/{id}/verdict` | `{answer, idempotencyKey}` → SOLVED/FAILED/WRONG/NEEDS_DETAIL |
| POST | `/sessions/{id}/abandon` | 진행 중 세션 포기 |

- 에러 응답은 `{code, message}`. `401` 토큰 없음/불일치, `404` 없음, `409` 다른 요청 처리 중·완료 세션·질문 한도 소진·진행 중 세션 존재, `422` 형식 오류·조사 불가 위치, `429` 호출량·예산 초과, `503` LLM 장애(미차감).
- 조사 요청은 클라이언트의 현재 좌표를 포함하고, 서버는 맵 경계·막힌 칸·오브젝트 거리·이동 속도를 검증한 뒤 위치도 갱신한다. 위치는 맵 이탈·주기적 체크포인트·조사·페이지 이탈 시 저장한다. 웹 MVP에서 완전한 치트 방어는 목표가 아니다.

## 9. 화면 구성
- **사건 선택:** 타이틀, 사건 카드 3개, 새로 시작/이어하기, 규칙·크레딧·개인정보 링크.
- **메인 추리:** 사건 개요서(수사 파일: 개요·관련자·타임라인), 질문 입력, 판정 이력, 남은 질문 횟수, `현장 조사`, 사건 수첩(사이드 패널), `정답 제출`(남은 기회 표시), 규칙 보기, 소리 설정.
- **현장 조사:** 픽셀아트 탑다운 타일맵, 격자 이동, 조사 표시, 단서 발견 모달, 추리 화면 복귀.
- **사건 수첩:** 확보한 단서와 이전 YES/NO/IRRELEVANT 질문 리스트(비공개 정답 미노출).
- **엔딩:** 성공/실패, 사건 해설, 미끼였던 단서, 통계. 해설은 판정 확정 후에만 전송.
- 와이어프레임·온보딩·글쓰기 가이드·아트 디렉션은 SPEC §14~15.

## 10. 테스트 및 출시 완료 기준
- 질문 정합성: 동일 의미 질문·부정문·함정 질문·프롬프트 인젝션 포함 평가(사건마다 평가 세트).
- 정확성: 질문 한도, CLARIFY·중복 미차감, idempotency 동일 응답, 동시 질문 409, 선점 만료 후 이중 차감 없음, LLM 오류 시 미차감과 재시도.
- 탐색: 충돌, 인접 조사, 단서 1회 획득, 재진입 시 복원, 조작된 좌표/오브젝트 요청 거부, 모든 오브젝트 도달 가능.
- 엔딩: 제출 3회·재작성 요청 2회 규칙, 종료 전 정답 비공개, 성공/실패 기준 검증, 클라이언트 번들에 정답 미포함.
- 다중 사건: 사건 간 세션 분리, 쉬움·어려움 사건이 코드 변경 없이 추가됨.
- 실행: Windows Git Bash에서 개발·테스트; 배포 환경에서 FE/BE/DB 정상 연결.
- 비용: LLM 호출 예산, 세션 질문·호출 상한, 요청 rate limit, 운영 비용 상한 설정.
- PRD에 없는 멀티플레이, 사건 에디터, NPC 심문, 로그인·랭킹, 힌트 시스템, 모바일 조작은 MVP에서 제외.
